# Проектная документация: система управления ПВЗ

Версия 1.2: 17.10.2026. Учебный год 2026/27.

Система нужна для приёмки, выдачи, возврата и обратной отгрузки отправлений, учёта хранения и анализа загрузки пунктов выдачи заказов. Сотрудники работают через сайт. Отчёт «Загрузка ПВЗ» строится в 1С по данным, выгруженным из PostgreSQL.

## Основание проекта

Кейс 9 «Пункты выдачи маркетплейса» из сборника «Кейсы для дисциплины “Основы проектной деятельности”», МИРЭА - Российский технологический университет, Москва, 2025. При подготовке использованы: §0–13 (с. 4–16), кейс 9 (с. 53–56), приложения B (с. 132–136), C9 (с. 145), D9 (с. 154), E и F (с. 159–161).

## Основные решения

1. Срок выпуска MVP - к 1 декабря 2026 года. Завершение разработки, итоговая защита и резерв исправлений - не позднее 31 мая 2027 года.
2. Серверная часть - Java и Spring Boot; основная база данных - PostgreSQL; пользовательский интерфейс - веб-приложение. Библиотеки для сайта и версии инструментов выбираем при настройке проекта и записываем в техническую документацию.
3. В 1С делаем форму импорта, справочники, регистр операций, отчёт с фильтрами и экспорт CSV. Если 1С недоступна, приёмка, выдача и возвраты продолжают работать.
4. Основные сценарии MVP: приёмка, выдача, возврат, отгрузка возвратов и анализ загрузки. Вход, справочники и загрузка данных обеспечивают выполнение этих сценариев.
5. Для проверки используются тестовые данные и ручной ввод кодов. Не подключаем реальные внешние системы, не используем данные настоящих клиентов и не запускаем систему в действующем ПВЗ.
6. Заказчик согласует объём, критерии и существенные изменения, принимает MVP и финальный продукт. Общение с Заказчиком ведёт тимлид - Владимир. Остальные решения и проверки берёт на себя команда.

## Как используем условия кейса

| Область | Принятое правило |
|---|---|
| Расчёт нагрузки | Почасовая модель основного текста кейса: количество успешных операций / паспортная мощность в операциях за час |
| Приложение C9 | Дневные данные рассматриваются отдельно; разница приёмки и выдачи за день in−out не используется вместо почасовой нагрузки. Для почасовой проверки необходимы дата и время каждой операции |
| Объём собственного набора T2 | 100 ПВЗ, ≥700 строк расписаний, ≥1000 отправлений, ≥5000 операций, ≥100 ячеек |
| Кафедральный T1 | Перед загрузкой проверяем формат файлов; дневные данные без времени операций проверяем отдельно |
| Календарь | Восьминедельный осенний цикл - разработка и защита MVP; февраль–апрель - развитие; май - финальные проверки и защита |
| Демонстрационные материалы | Презентация из 7 слайдов, видео продолжительностью 3–5 минут, протокол приёмки |

## Как меняем требования

После второй недели новые требования записываем отдельной задачей `scope-change` и в [реестре изменений](change-requests.md): зачем нужно изменение, что придётся переделать и сколько времени это займёт. Аналитик и тимлид рассматривают задачу. Если меняются набор функций, сроки или условия приёмки, Владимир согласует решение с Заказчиком. Обязательные функции MVP сохраняются. После 30 апреля 2027 года новые функции не добавляем - занимаемся проверками, исправлениями и защитой.
