# Требования и MoSCoW

Версия 1.2: 17.10.2026.

**Источники требований:**

- **К** - кейс и методические требования.
- **П** - бизнес-потребности проекта.
- **Д** - решение команды.

**Приоритеты MoSCoW:**

- **Must (M)** - обязательны к 01.12.2026; без них MVP не принимается.
- **Should (S)** - требования полной версии к маю.
- **Could (C)** - дополнительные возможности при наличии свободного времени.
- **Won’t (W)** - не входят в проект этого учебного года.

Приоритеты относятся ко всему проекту. Срок указан для каждого требования.

Изменение обязательных требований оформляем отдельной задачей `scope-change`.

Подготовка списка требований - Владимир; проверка и уточнение требований - Алексей.

## 3. Как учитываем отправления

В MVP каждое отправление имеет свой код, объём и место хранения. Частичную выдачу и заказы из нескольких товаров не делаем. Отправления и коды получения и возврата заранее создаём в тестовых данных, без связи с маркетплейсом.

Объём задаём в литрах, больше нуля. Для MVP сравниваем сумму объёмов с вместимостью ячейки. Форму и размеры упаковки такая проверка не учитывает; проверку габаритов можно добавить весной.

Основной путь: ожидается (`EXPECTED`) → хранится в ПВЗ (`STORED`) → выдано (`ISSUED`). Возврат: `ISSUED → RETURN_STORED → RETURN_SHIPPED` по отдельному коду возврата. Невостребованный: `STORED → RETURN_STORED → RETURN_SHIPPED` по истечении срока в расширенной версии; в MVP перевод в возврат допускается по заранее заданному учебному основанию. Если отправление остаётся в ячейке, повторное резервирование объёма не выполняется.

Операции разрешены только в часы работы: время открытия включается, время закрытия - нет. Например, при графике 09:00–18:00 операция в 09:00 разрешена, а в 18:00 уже запрещена. Если на этот день расписания нет, операции запрещены. Причина отказа записывается в журнал.

В MVP используем расписание без ночных смен, с началом и концом в целый час. Часы работы не пересекаются. В выгрузке сохраняем расписание и допустимую нагрузку на момент отчёта, чтобы новые настройки не меняли результаты прошлых проверок.

Успешная приёмка - одна in; выдача - одна out; приём возврата/перевод невостребованного - одна return. Подтверждение обратной отгрузки записывается в аудит отдельным действием `return_dispatch`, но не добавляет второй return в нагрузку.

У отгрузки два статуса: черновик (DRAFT) и отправлена (SHIPPED); одно отправление не может одновременно входить в две активные отгрузки. Вся отгрузка подтверждается целиком. Если возникла ошибка, её состав и статусы не меняются. Повторное подтверждение не освобождает место второй раз. Статус отправления, запись в журнале и занятое место меняются вместе: сохраняются все изменения или ни одно.

## 4. Как считаем загрузку

`ops_per_hour` - число успешных событий in/out/return; это поток операций, а не остаток посылок. `load_pct = 100 × ops / capacity`. Перегрузка - строго `load_pct > 100`; 100% ещё не перегрузка. При фильтре типа числитель ограничивается типом, знаменатель остаётся общей мощностью и показатель обозначается как вклад типа. Общая доля перегрузки рассчитывается без фильтра типа.

Для рабочих часов без операций формируются строки ops=0, load=0. Закрытые часы не входят в знаменатель KPI. Пустая выборка - «нет данных». Отчёт дня: ops=sum(hour.ops), capacity=sum(hour.capacity), load=100×ops/capacity. Пустые рабочие часы необходимо генерировать по расписанию, а не только по имеющимся событиям.

CSV почасового отчёта: `pvz_id,date,hour,ops,capacity,load`; load - доля (1.25=125%), а не число процентов. Флаг перегрузки отображается в отчёте; расширенный CSV может добавлять `overload_flag` по согласованной версии схемы. День экспортируется отдельно с явным указанием, что это дневной отчёт без фиктивного часа.

Заполненность хранения: `100 × занятый_объём / доступный_объём`. Она выводится отдельно от операционной нагрузки и не заменяет KPI кейса. Рекомендации о продвижении - гипотеза: слабая нагрузка не доказывает низкую узнаваемость. MVP показывает факт; расширенная версия предлагает проверить причины и соседние точки из заданного справочника, без обещания эффекта и без геосервиса.

## 5. Минимальные технические форматы данных

Состав API: GET `/api/pvz`, GET `/api/shipments/{code}`, POST `/api/receipts`, POST `/api/issues`, POST `/api/returns`, POST `/api/return-dispatches`, POST `/api/return-dispatches/{id}/confirm`, GET `/api/exports/operations`. Каждый запрос изменения данных содержит ключ повтора (`idempotency key`). Повтор с тем же ключом и тем же телом возвращает сохранённый результат без повторного выполнения действия. Запрос с тем же ключом и другим телом отклоняется с кодом 409. В ответе возвращаются ID, статус и результат. Ошибки: 400 - формат; 401 - нет входа; 403 - нет прав; 404 - неизвестное отправление; 409 - конфликт состояния/вместимости. [OpenAPI](../spec/openapi.yaml) описывает реализованные вход, чтение точек и ячеек, поиск отправления, приёмку и выгрузку. Остальные операции добавляются по мере реализации.

Состав объектов 1С: справочник `ПВЗ` (идентификатор, регион, мощность), регистр сведений `РасписаниеПВЗ`, регистр сведений `ОперацииПВЗ` с уникальным op_id, обработка `ЗагрузкаСнимкаПВЗ` с формой выбора файлов и протоколом, отчёт `ЗагрузкаПВЗ`. Роли 1С ограничивают точки/регионы так же, как сайт; операционный аналитик видит сеть. Сначала данные загружаются во временное хранилище и проверяются. После успешной проверки весь набор становится доступен для отчёта. При ошибке сохраняется предыдущий набор. Нельзя подключать форму 1С напрямую к таблицам PostgreSQL для записи.

## 6. Порядок работ и изменение требований

До 31 мая закрываются утверждённые Should; дополнительные требования после заморозки объёма 30 апреля переходят за границы текущего проекта.
